An interactive explainer

How do you know a language model is good enough?

Every few months a new model shows up: faster, cheaper, smarter, or so they say. Before we switch, we want proof, not a hunch. This is how we get it: with benchmarks, and the small tool we built to run them.

Part one: what a benchmark is and how ours work. No code.
Part two: building one yourself.

Step 1 · What is a benchmark?

An exam for a model

Trying a model by hand a few times tells you how it felt. A benchmark tells you how it did: the same questions, asked the same way, graded by the same rule, with every result written down. Tap each part to see an example.

The exam is what makes models comparable. A model tried by hand is a story; two models that sat the same exam are two numbers you can put side by side.

Step 5 · Rows become inputs

The factory's loading dock

From here on, picture a benchmark as a factory. The data file is the loading dock: each row is stamped into an input card and put on a conveyor belt. Machines will work on it, and inspectors will watch. Tap a card to read it.

Rows go in one at a time: the first card is on its way while most of the file is still unread, so ten rows or a million make no difference. Each kind of data brings its own dock (a spreadsheet reader here, a database elsewhere), but the belt only ever sees cards.

Step 6 · The machines

Our server answers, a machine checks

Each card goes into a black box: our own server running Gemma or Qwen, which writes a new answer. Then the validator puts that answer next to Gemini's and stamps ✓ or ✗. Probes time every box; inspectors count every card.

These machines are the benchmark's steps. Each one only sees the card in front of it, does one job and passes it on, and every step is timed without anyone asking. Swap the machines and you have a different benchmark on the same belt.

Step 7 · Checking the answer

A cheap check first, a judge when it matters

Comparing words is instant but strict: “4,320 minutes” is right, yet it isn't “4320”. So first a free exact check: identical answers are settled and drop off. Only the rest go to the judge, another LLM we ask whether our answer is correct.

  • 0 completed went through every station
  • 0 stopped settled early, on purpose
  • 0 failed kept, with the reason

The judge is slow and costs money (watch its probe), so it only sees the cards that need it. When the server breaks, the card isn't lost: it ends as failed, with the reason, and the belt keeps moving.

Your turn

What you write to make a benchmark

The factory is built. A new benchmark is a handful of decisions, in this order: where the data comes from, what one input looks like, the steps, and how to run it. No Python, just what each piece needs.

Where the inputs come from, and how to read them

The first decision. Your data can live anywhere; the source is the one piece that knows where, and turns it into inputs, one at a time.

A source

Yours to write, one per kind of data. Behind it, the rest of the benchmark never knows whether the inputs came from a file or a database: swap the source and nothing else changes.
